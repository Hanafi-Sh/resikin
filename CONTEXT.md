# ResikIn

ResikIn is a waste reporting and coordination system for Kota Yogyakarta. This context describes the domain language around citizen reports, field assignments, and cross-channel reporting.

## Language

**Laporan Intake**:
The process of accepting a new waste report from web or Telegram until it is validly stored with an initial status.
_Avoid_: report lifecycle, intake flow

**Laporan Terkirim**:
A waste report that has passed intake validation and is stored with status `dikirim`.
_Avoid_: pending report

**Draf Laporan**:
An incomplete report being collected in a channel before it becomes a Laporan Terkirim.
_Avoid_: pending report, user state

**Kode Tracking**:
A public identifier generated for a stored waste report so the reporter can follow its status.
_Avoid_: manually assigned tracking number

**Pelapor**:
A resident who submits a waste report through web or Telegram.
_Avoid_: reporter, user

**Foto Laporan**:
Visual evidence submitted by a Pelapor as part of a waste report.
_Avoid_: attachment

**Validasi Foto Laporan**:
The process of checking whether a Foto Laporan is likely to show a waste issue before the photo is accepted into a Draf Laporan.
_Avoid_: AI chat validation, image moderation

**Foto Penyelesaian**:
Visual evidence submitted by a petugas when completing assigned work.
_Avoid_: completion attachment

**Galeri Laporan**:
The display-ready collection of report and completion photos for a stored waste report, regardless of storage source.
_Avoid_: report_photos, attachments

**Kelurahan Laporan**:
The kelurahan associated with the waste report location.
_Avoid_: area, region

**Alur Penanganan Laporan**:
The operational process of moving a stored waste report through statuses until it is completed or rejected.
_Avoid_: report workflow, status update

**Notifikasi Laporan**:
A notification sent to a relevant party when a report is created, assigned, or changes status.
_Avoid_: webhook event, bot message

## Relationships

- A **Laporan Intake** creates exactly one waste report.
- A **Laporan Intake** produces a **Laporan Terkirim** when it succeeds.
- A **Draf Laporan** or incomplete Telegram conversation is not a **Laporan Terkirim**.
- A **Laporan Terkirim** has exactly one **Kode Tracking** generated by the database.
- A **Laporan Terkirim** has exactly one **Pelapor**.
- A web **Pelapor** is stored as a name/phone snapshot on the report.
- A Telegram **Pelapor** may be remembered as a reporter record and referenced by the report.
- A **Laporan Intake** may include one or more **Foto Laporan** from web storage URLs or Telegram file identifiers.
- A **Draf Laporan** may use **Validasi Foto Laporan** before accepting a Telegram **Foto Laporan**.
- **Validasi Foto Laporan** does not replace the Pelapor's selected report category.
- **Alur Penanganan Laporan** may add one or more **Foto Penyelesaian** when work is completed.
- A **Galeri Laporan** may contain **Foto Laporan** and **Foto Penyelesaian** from different storage sources.
- A **Laporan Terkirim** should have a **Kelurahan Laporan** when it can be determined, but web intake may temporarily store reports without one.
- A **Laporan Terkirim** enters the **Alur Penanganan Laporan** after intake.
- **Alur Penanganan Laporan** is separate from **Laporan Intake**.
- The normal **Alur Penanganan Laporan** status path is `dikirim -> diterima -> ditugaskan -> dalam_proses -> selesai`.
- A coordinator may assign directly from `dikirim` to `ditugaskan`.
- A report may move to `ditolak` from `dikirim`, `diterima`, `ditugaskan`, or `dalam_proses`.
- `selesai` and `ditolak` are terminal statuses.
- A koordinator verifies, assigns, or rejects reports in the **Alur Penanganan Laporan**.
- A petugas moves assigned work from `ditugaskan` to `dalam_proses` and then to `selesai`.
- Assigning a report to a petugas and moving it to `ditugaskan` is one atomic domain action.
- The explicit actions in **Alur Penanganan Laporan** are accept, assign, start work, complete work, and reject.
- **Laporan Intake** and **Alur Penanganan Laporan** may produce **Notifikasi Laporan** after the database mutation succeeds.
- Canonical **Notifikasi Laporan** event names are `report.created`, `report.assigned`, and `report.status_changed`.

## Example dialogue

> **Dev:** "Does **Laporan Intake** include assigning a petugas?"
> **Domain expert:** "No. **Laporan Intake** ends once the report is validly stored with its initial status."
>
> **Dev:** "Should a partially completed Telegram report be saved as pending?"
> **Domain expert:** "No. It is a **Draf Laporan** until it becomes a **Laporan Terkirim**."
>
> **Dev:** "Should the web app generate the **Kode Tracking** before saving?"
> **Domain expert:** "No. The database generates the **Kode Tracking** when the report is stored."
>
> **Dev:** "Is a Telegram sender different from a web form submitter?"
> **Domain expert:** "Both are **Pelapor**. Telegram may remember them, but the domain role is the same."
>
> **Dev:** "Should web form submitters become remembered reporter records?"
> **Domain expert:** "Not during **Laporan Intake**. Web keeps a snapshot; Telegram may use a remembered record."
>
> **Dev:** "Are web photos and Telegram photos different domain concepts?"
> **Domain expert:** "No. Both are **Foto Laporan**, even though they are stored through different channels."
>
> **Dev:** "Is a petugas completion photo a **Foto Laporan**?"
> **Domain expert:** "No. It is a **Foto Penyelesaian** because it proves handling, not intake."
>
> **Dev:** "Should UI code care whether a photo came from Telegram or Supabase Storage?"
> **Domain expert:** "No. UI should consume the **Galeri Laporan**."
>
> **Dev:** "Should web reports be rejected if the kelurahan cannot be determined yet?"
> **Domain expert:** "No. Store the report, but treat the missing **Kelurahan Laporan** as an intake gap to fix later."
>
> **Dev:** "Is assigning a petugas part of **Laporan Intake**?"
> **Domain expert:** "No. Assigning a petugas belongs to **Alur Penanganan Laporan**."
>
> **Dev:** "Can a completed report be moved back to in progress?"
> **Domain expert:** "No. `selesai` and `ditolak` are terminal statuses."
>
> **Dev:** "Can a petugas reject a report?"
> **Domain expert:** "No. A petugas handles assigned work; rejection is a koordinator decision."
>
> **Dev:** "Can a report be `ditugaskan` without an assignment?"
> **Domain expert:** "No. Assigning the report and creating the assignment happen together."
>
> **Dev:** "Should callers directly set any status they want?"
> **Domain expert:** "No. Callers perform explicit actions such as accept, assign, start work, complete work, or reject."
>
> **Dev:** "Should Telegram be notified before a report mutation commits?"
> **Domain expert:** "No. A **Notifikasi Laporan** is sent only after the report mutation succeeds."
>
> **Dev:** "Can notification event names be arbitrary strings?"
> **Domain expert:** "No. Use the canonical **Notifikasi Laporan** events."

## Flagged ambiguities

- "report lifecycle" was used ambiguously for both initial report creation and later status changes. Resolved: this planning thread uses **Laporan Intake** for initial creation only.
- `pending` appeared in an older bot migration, but the domain term for a stored new report is **Laporan Terkirim** with status `dikirim`.
